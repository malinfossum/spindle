# Spindle v0.2 — plan

Spec of record for v0.2, same as `v0.1-plan.md` was for v0.1. v0.1.0 is
released; everything below is what comes after it.

The theme of v0.2 is that Spindle stops being a folder of scripts and becomes a
built, deployable app — without giving up the thing that makes it Spindle: the
library never leaves the device.

## Shipped

### 1 — every action goes through `data-action`

70 inline `on*` attributes across 13 files are gone. The View no longer carries
behaviour, which is the MVC rule the rest of the app already followed.

- **`View/Universal/bindActions.js`** — one delegated listener per event type,
  bound to `document`. `updateView()` replaces `#app` wholesale, so a listener
  bound to rendered markup would be thrown away with it; delegation also means
  freshly rendered markup is live immediately and nothing is ever re-bound.
- **`Controller/Universal/actions.js`** — `ACTIONS`, the map of 38 named
  handlers, wired once by `initActions()`.

Attribute per event type, so one element cannot answer to two:

| Attribute | Event |
|---|---|
| `data-action` | `click` |
| `data-action-input` | `input` |
| `data-action-change` | `change` |
| `data-action-submit` | `submit` |
| `data-action-toggle` | `toggle` |

Arguments ride as `data-*` attributes beside the name (`data-page`, `data-id`,
`data-index`, `data-panel`, `data-lang`, `data-edit`). The two that reach
further into the app are whitelisted where they land — `navigate()` against
`model.app.allPages`, `setLang()` against `LANGUAGES` — and `data-panel` goes
through the `FORM_PANELS` lookup rather than indexing the model by a string
taken from markup.

Two things fell out of the move. `closest()` stops at the nearest element
carrying the attribute, so a button inside a clickable card answers for itself
and the card never hears about it — that is what the album card's
`event.stopPropagation()` calls were hand-rolling. And an action name with no
handler now warns on the console instead of being a button that silently does
nothing.

### 1b — semantics, and then the CSP

Three clickable things were not keyboard-reachable, and two "links" were not
links. All five are fixed:

- **Brand.** `<h1 onclick>` → `<h1><button class="brand-btn"></h1>`. Note the
  rule is `.Navbar .brand-btn`, not `.brand-btn`: `.Navbar button` is (0,1,1)
  and outranks a single class, so the plain selector silently lost the cascade.
- **Album card.** The card holds two buttons, so it cannot be one. The title is
  now the real control and `.album-open::after` is stretched over the whole card
  — one tab stop named after the album, with the entire card as its pointer
  target, and `.album-actions` raised back above the overlay. This is the same
  pseudo-element trick that does *not* work for segmented controls: there,
  adjacent expanded areas overlap and steal each other's clicks; here each
  overlay is bounded by its own card.
- **Profile card.** No nested buttons, so the whole tile simply *is* the button.
  Innards became spans, because `<button>` only takes phrasing content — the
  stylesheet gives them back `display: block` or the ellipsis truncation stops
  working.
- **Auth "links".** `<a href="#">` → `<button class="link-inline">` and
  `<button class="auth-back">`. They move between pages of a single-page app;
  there was never a URL to follow, and the `href="#"` only ever pushed a stray
  fragment onto the address bar.

With no inline handlers left, the two inline `<script>` blocks were the last
thing standing between Spindle and a real Content-Security-Policy. Both are now
files — `themePreload.js` (still synchronous in `<head>`, still
duplicating the prefs key on purpose, so there is still no theme flash) and
`Controller/Universal/theme.js` + `Controller/Universal/boot.js`. That buys a
`script-src` of plain `'self'` with **no hashes to keep in sync**, which is the
whole reason for preferring a file over an inline script plus `'sha256-…'`.

The policy now ships as a `<meta http-equiv>` in `index.html`. It is enforced:
an injected `<script>` and an external `https://` script are both blocked.

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self'; connect-src 'none';
object-src 'none'; base-uri 'none'; form-action 'none'
```

`style-src` still needs `'unsafe-inline'` for the eleven `style=""` attributes
that carry render-time values (the storage bar's width, the chip panels'
visibility). Injected CSS is a far smaller prize than injected script; removing
them is its own job and not a blocker.

### 2 — Vite, Biome, and ES modules

Three commits, in the order the plan called for.

**`biome.json` and the reformat, alone in one commit.** Tabs, LF, final
newline, width 100 — the same rules `.editorconfig` already stated. Only JS,
CSS and JSON are in scope: Biome's HTML formatter is still experimental, and
`index.html` was not worth handing to a beta. `package-lock.json` is excluded,
because npm rewrites it with its own formatting on every install.

One recommended lint rule is off, for a reason that does not expire:

- `suspicious/noDuplicateProperties` flagged the deliberate
  `min-height: 100vh` → `100dvh` fallback pair. It cannot tell a
  progressive-enhancement fallback from a mistake, so it stays off.

`correctness/noUnusedVariables` was off for the same commit, for the reason
above — 91 top-level functions looked like dead code to a linter that could
not see the `<script>` tags calling them. It was turned back on in `e838110`,
once the module graph gave every function a real caller to be found by, and it
found real dead code: 13 `==` comparisons, 7 `!important` declarations, 5
optional-chain suggestions and one `parseInt` without a radix were cleared in
that commit. Zero of each remain.

`.gitattributes` also gained `eol=lf` on checkout. The index was already LF,
but `core.autocrlf` handed CRLF back to the working tree, so every formatter
run rewrote endings git then reported as clean.

**Vite, with all 41 `<script src>` tags untouched.** A no-op in the browser, as
predicted. The CSP needed less relaxing than feared: only the HMR websocket is
blocked, by `connect-src 'none'`, because Vite's dev client is a real file and
`script-src 'self'` already covers it. So `vite.config.js` rewrites that one
directive while serving, instead of stripping the whole meta tag — the rest of
the policy stays enforced in development. `npm run build` did not produce a
working app at this commit, and was not made to: Vite refuses to bundle a plain
`<script src>` without `type="module"` and drops it, which is exactly what the
module conversion fixes.

**ES modules.** 41 script tags collapsed to one:
`<script type="module" src="Controller/Universal/boot.js">`. Every file exports
only what another module actually reads, and imports what it uses; `boot.js`
imports `storageSync.js` for its side effect alone, since that module registers
the cross-tab `storage` listener and exports nothing. `navbar&Mobile.js` became
`navbarMobile.js` before the `&` could become an import specifier.

`themePreload.js` moved to `public/themePreload.js` and is loaded as
`/themePreload.js`. It is the one file Vite must not touch: `public/` is copied
to the output verbatim, and anything Vite bundles becomes a module — deferred by
definition, which is the theme flash all over again. The rest of the app is a
module graph; that file deliberately is not part of it.

**What the conversion made visible.** Ten View files imported from Controller,
and `Model/i18n/i18n.js` imported `updateView` from View. Under `<script>` tags
these were invisible global calls; as imports they became edges in a graph, and
they pointed the wrong way for MVC. Nothing was refactored to fix that in this
commit — it would have stopped being a mechanical conversion — but the list was
short and got its own pass later in this branch (`4b1f427`, `744f45e`,
`bfdec26`, `13aa20d`): `Model/selectors.js` took the five derived reads
(`getLoggedInUser`, `isLoggedIn`, `getAccessibleAlbums`, `getProfileAlbums`,
`getSearchResults`) that had been filed under Controller/Login and
Controller/Search though they touch no DOM and change nothing, which is what
the View files were really reaching across for; `Controller/Universal/router.js`
took `changePage()` out of `View/Universal/updateView.js`, and `Model/viewState.js`
took the four transient-state resets `changePage()` used to call by name; and
`Model/i18n/i18n.js` stopped importing `updateView` from the View by handing
the re-render decision to the Controller, with `View/Universal/chrome.js`
taking over the chrome-syncing that move needed. The import direction the
conversion exposed is fixed — see **Layering** under Conventions added in
v0.2.

**Verified**, dev and built output both: register creates the seeded library,
save adds an album, validation blocks an incomplete one, login decrypts after a
reload, encrypted export downloads, language and theme switch and survive a
reload. The built bundle still blocks an injected inline script, so the CSP
survived the move. The confirm-dialog flows cannot be finished in this preview
pane — `<dialog>`'s `close` event never fires without compositing — so deletion
was confirmed only as far as the dialog opening.

### Also fixed on the way past

The navbar overflowed a 375px viewport by 4px in English **before** any of this
work — the theme toggle was pushed off the right edge, and the v0.1 "zero
horizontal overflow" check missed it because the preview pane reports a 0×0
viewport unless the tab is explicitly resized. Root cause was flexbox: a flex
item defaults to `min-width: auto` and refuses to shrink below its content, so
a longer label pushed the row wider instead of narrowing the search box.
`.nav-mobile` and `.Navbar input` now carry `min-width: 0`, and the navbar's
mobile side padding dropped from `1.5rem` to `0.75rem` (restored at 768px).

Verified at 375 / 768 / 1280 in both languages: zero horizontal overflow, every
target ≥ 44×44 except the two documented exceptions (a bare checkbox — the
wrapping `<label>` is the target — and inline links inside a run of text).

### 3 — hash routing

Pages are linkable and the back button works. `#about` pasted into a fresh tab
opens on the about page; Back walks the pages visited and Forward walks forward
again. Deep links land as typed for the five names in `model.app.publicPages` —
`welcome`, `login`, `register`, `about`, `notFound`. Every other fragment
resolves to `#welcome` until the library is unlocked, because a fresh tab is
always locked; see the third limitation below. The fragment is `#<pageName>`
using the names already in `model.app.allPages` — no leading slash, no prettier
second vocabulary to keep in sync — and an empty fragment means `welcome`, the
value `currentPage` already started on. The auth "links" stopped writing `#` to the URL in 1b, so the
fragment was free to own.

`changePage()` is gone as a name; all 13 call sites call `navigate()`. Keeping
both would have left a way to change page without changing the URL.

**`navigate()` renders; the listener is for URL changes the app did not make.**
The obvious split is the other one — write the hash, let `hashchange` render —
but that event is queued, not synchronous, so it would make every call site
asynchronous. `backup.js` is the proof: it navigates to `login`, sets
`backup.importDone`, then renders. A deferred resolve would render the page it
was leaving and then wipe the message it exists to show. So `navigate()` writes
the fragment and resolves it in the same turn, and `hashchange` handles back,
forward and a fragment typed into the address bar. `lastResolvedHash` tells the
echo of the router's own write from a real traversal — it is compared against
what the address bar actually says rather than counting suppressed events, so it
cannot drift. Exactly one render per navigation, which is the thing to protect.

Four traps shaped the rest:

- **Assigning `location.hash` a value it already holds fires nothing.** So
  `navigate()` resolves unconditionally rather than waiting for an event that
  will not arrive. Several call sites depend on it: `logout()` sends you to
  `login` from `login`, and `deleteAlbum()` re-enters `homePage` from `homePage`
  to drop the row it just deleted. A router that skipped the re-render because
  the page name matched would leave the deleted album on screen.
- **The auth guard rewrites the URL, with `replaceState`.** It used to render
  `welcome` while leaving the requested page in `currentPage`'s place silently;
  with URLs that would mean an address bar reading `#profile` over a welcome
  page. Pushing instead of replacing would trap the visitor — Back returns to the
  URL that redirects, which redirects forward again.
- **An unknown fragment keeps its URL.** Deliberately the opposite of the guard:
  someone who mistyped needs to see what they typed, so `#nonsense` renders the
  not-found view under `#nonsense` and only the console warning names it.
- **The fragment is attacker-supplied.** It is decoded inside a `try`/`catch` —
  a malformed escape like `#%E0%A4%A` throws, and an uncaught throw in a
  `hashchange` handler leaves the app frozen on the page it was showing — and it
  still passes `model.app.allPages.includes()` before it can reach the model.
  Nothing interpolates it into HTML and nothing indexes the model with it.

Three documented limitations:

- **No session survives a page load, so a guarded deep link always redirects.**
  This is the largest practical limit on the feature, and it is the encryption
  model rather than the router: `isLoggedIn()` reads `model.app.crypto.unlocked`,
  which starts `false` and is set only by `login()` and `register()`. The keys
  live in memory and are never persisted — that is the point — so a new tab, a
  reload and a restored window are all locked, and `#profile` in any of them
  resolves to `#welcome`. Linkable therefore means the five public pages today.
  Making the rest linkable would mean unlocking without the password, which is
  not a trade this app makes; the honest improvement is to remember the requested
  page across the unlock and land there afterwards, which is its own task.
- **Detail pages deep-link to the library.** `viewDetails` and `editDetails`
  render whichever album `model.viewState` holds, and a cold link has no
  selection. They route by name like every other page and fall back to
  `homePage` — same replace-not-push treatment as the guard — when the selection
  is not live. `hasSelectedAlbum()` in `selectors.js` also catches a selection
  left pointing at an album that has since been deleted. Putting an id in the URL
  would mean giving albums stable public identifiers, and that is a product
  decision nobody has made.
- **Nav controls are still `<button>`, not `<a href="#page">`.** Now that pages
  have URLs the semantics convention argues for links, and that argument is
  correct — but it touches every nav control plus its CSS, and both goals above
  are met without it. v0.3.

Two more for v0.3, both found reviewing this item rather than using it:

- **`pushState` would delete the echo problem outright.** `navigate()` changes the
  URL with `window.location.hash = target`, and that is the only reason an echo
  exists: it fires a `hashchange` for a navigation the router has already
  rendered, which is what `lastResolvedHash` is for.
  `window.history.pushState(null, "", target)` pushes the same history entry and
  shows the same URL but fires nothing, while Back and Forward across those
  entries still fire `hashchange` normally — so `onHashChange()` would keep
  working untouched and `lastResolvedHash`, its comment budget and its ordering
  invariant would all go away. It would also let `navigate()` resolve *before*
  pushing, so a redirected navigation pushes one entry instead of pushing and
  then replacing. Not done here on purpose: the shipped version was traced
  through the adversarial back/forward sequences and holds, and rewriting the
  navigation core of the highest-risk file before it has been used in a browser
  trades verified for tidier.
- **Back is pressable while a confirm dialog is open.** `delete.js` awaits
  `openDialog()` before navigating, so a Back press during that await re-renders
  `#app` underneath the open modal. The dialog itself survives — `dialog.js`
  appends to `document.body`, not `#app` — but on close it calls
  `opener.focus()`, and the opener button was destroyed by the re-render, so
  focus lands on `<body>` with nothing announced. Same class as the `set-lang`
  regression fixed earlier in v0.2, and not a router defect: any re-render during
  an open dialog does it. The fix belongs with the dialog, which should resolve
  or re-target its focus restore when its opener is gone.

## 4 — Deploy + security headers

**Cloudflare Pages, not GitHub Pages.** GitHub Pages cannot set response headers
at all, which is why the policy currently lives in a `<meta>` tag —
and `frame-ancestors` cannot be expressed there, so clickjacking protection is
simply missing until this lands. Cloudflare Pages sets real headers via
`_headers`, and it is coherent with the Cloudflare Registrar plan for
`malinfossum.dev`.

Starting point for `_headers` — the same policy plus the parts a `<meta>` tag
cannot carry:

```
/*
  Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()
  Cross-Origin-Opener-Policy: same-origin
```

Remove the `<meta>` tag once the header is live so there is one policy, not two
that can drift.

**No database, by design.** `localStorage` plus client-side AES-GCM is the
security model, not a stepping stone to a backend. Adding a server database
would break the property the app is built around.

## 5 — Plaintext import

Still deferred, and the honest assessment is that it should be dropped. It means
validating an untrusted library field by field — the highest-risk surface in the
app — for the lowest user value, given that encrypted import already covers
"move my library to a new browser".

## Conventions added in v0.2

These join the `v0.1-plan.md` conventions, which all still hold except the two
noted below.

**Actions.** No inline `on*` attributes, ever. A new interactive element gets a
`data-action*` attribute and an entry in `ACTIONS`. Arguments go in `data-*`
attributes, never interpolated into executable strings. Anything from an
attribute that indexes into the model goes through a lookup, not a bare key.

**No inline scripts.** This supersedes the v0.1 "Theme" and "Boot order"
conventions, which described both as inline blocks in `index.html`. They are
`public/themePreload.js` and `Controller/Universal/boot.js` now. An
inline script would force `'unsafe-inline'` and undo the CSP.

**Semantics.** Actions are `<button>`, navigation is `<a>`. A clickable `<div>`
is a bug. Where a whole card must be clickable but contains its own buttons, use
the stretched-`::after` pattern on the card's primary control — never
`role="button"` plus `tabindex`.

**Modules.** One entry point, `Controller/Universal/boot.js`. A file exports
only what another module reads; anything else stays private. `public/` is for
the files Vite must not transform, and today that is exactly one —
`themePreload.js`, which has to stay a classic synchronous script.

**Routing.** The app changes page by calling `navigate()`, never by writing
`model.app.currentPage` or calling `updateView()` for a page change — those two
are how a screen and its URL drift apart. A new page is a name in
`model.app.allPages`, a branch in `updateView()`, and an entry in
`model.app.publicPages` if a locked library may open it; the fragment is the
same name, and nothing else needs a route table. `Controller/Universal/router.js`
is the only file that touches `location` or `history`. A redirect the visitor did
not ask for replaces the history entry; a page they typed wrong keeps it.

**Layering.** Allowed edges are View → Model and Controller → (Model, View);
View → Controller and Model → View are forbidden. The ES-module conversion
turned the app's global function calls into import edges and made the ten
View → Controller imports and the one Model → View import (`i18n.js` calling
`updateView`) visible for the first time; this branch's pass (`4b1f427`,
`744f45e`, `bfdec26`, `13aa20d`) closed all of them by moving the behaviour
those imports were reaching for into `Controller/Universal/router.js`,
`Model/selectors.js`, `Model/viewState.js` and `View/Universal/chrome.js`. The
import graph is clean as a result — zero View → Controller, zero Model → View,
zero Model → Controller edges remain.

The import direction was fixed first, and the layer contract followed. Moving
imports did not move the View code sitting inside Model files, and it left four
cases standing: `applyLang()`, `applyStaticText()` and `langSwitcher()` in
`Model/i18n/i18n.js`, and `renderStrength()` in `Model/auth.js`. None of them
crossed a module boundary — the DOM access was local to the file that also
exported Model state — which is why the import graph read clean, but the layer
rule is about what a file *does*, not just what it imports, and by that measure
all four were View code wearing a Model file's name.

Three have now moved. `applyLang()` and `applyStaticText()` joined
`syncNavbar()` and `syncChrome()` in `View/Universal/chrome.js`, which was
already patching the same static navbar and footer. `langSwitcher()` is
`View/Universal/langSwitcher.js` — it returns an HTML string rendered inside
`#app`, not a patch applied outside it, so it sits beside `backup.js` as the
second fragment both the welcome page and the profile page embed, rather than
in `chrome.js`. `renderStrength()` is in `View/Register/view.js`, next to the
markup it patches.

Two edges had to be cut for that to be legal. `setLang()` called `applyLang()`
itself, which after the move would have re-created the Model → View import this
branch had just removed; it now writes the preference and stops, and the
`set-lang` handler in `Controller/Universal/actions.js` calls `applyLang()` and
then `updateView()`. Its early return — do nothing when the chosen language is
already active — stays first and unchanged; re-rendering would destroy the
button the user just pressed and drop focus to `<body>`. And `langSwitcher()`
read the module-private `LANGUAGES` table for one `lang` attribute; `i18n.js`
exports `getHtmlLang(code)` for that field alone, so the string tables and seed
lists stay in the Model. `Model/i18n/i18n.js` now contains no DOM access at all.

`renderStrength()` also carried a bug that shipped: it wrote
`Passordstyrke: N av 4` as a literal, past `t()`, so the password-strength
readout stayed Norwegian for an English user even though `auth.strength`
existed in both string files with a `{level}` parameter. It uses the key now.
The move ended what caused it — `registerPage()` rendered the meter correctly
while `renderStrength()` reimplemented it, and each carried its own copy of the
`bar-on` / `bar-off` rule. Both go through one `barClass()` in the View, so the
first render and the per-keystroke patch cannot drift again. `renderStrength()`
still patches the DOM rather than re-rendering, for the same reason the
`set-lang` guard exists: `updateView()` replaces `#app`'s innerHTML and would
drop focus out of the password field on every keystroke.

Two things about the strength meter are unchanged and worth naming.
`registerPage()` renders five bars while `passwordStrength()` returns
`Math.min(score, 4)` and the string reads "of 4", so the fifth bar can never
light — consistent in both paths, and a visual-design decision rather than a
layering one. And switching language mid-typing now
follows: `updateView()` re-renders the whole register page from
`model.viewState.createProfile`, so the typed password, the bars and the
readout all come back in the new language, and the next keystroke reads the new
language too because `t()` resolves at call time. The cost is the focus drop
every re-render of `#app` causes, which is not specific to this field.

Still open: `model.js:3` holds a live DOM node
(`document.getElementById("app")`) rather than a reference a View file looks up
itself. Left for v0.3.

**Verifying layout.** The preview pane reports a 0×0 viewport by default, which
makes every geometry measurement meaningless — including target sizes and
overflow. Set the viewport explicitly before measuring, and check 375 / 768 /
1280 in both languages.
