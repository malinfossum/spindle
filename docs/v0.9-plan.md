# Spindle v0.9: plan

Spec of record for v0.9. v0.8 is closed: the crop dialog turns and straightens
a cover, and it shipped in `9a0b466`.

v0.9 lets me delete a library from inside the app. Today there is no way to
remove one. A forgotten password leaves a library nobody can open, and the only
way out is clearing the site's data in the browser settings, which most people
will never find. v0.9 is the last feature before I call Spindle finished.

**Status:** designed and stress-tested 2026-10-12 (security, privacy,
accessibility, legal, loopholes). Its fixes are folded into §§ 1–8, and what I
chose not to fix is in § 10. Built on branch `v0.9`.

---

## 0. Decisions

| # | Question | Decision |
|---|---|---|
| 1 | Where can I delete the library from? | **Profile, and a "Can't open the library?" panel on the login page.** A forgotten password or a damaged library is exactly when I am stuck today. The login path needs no password, and that gives nobody new power: anyone holding the device can already clear the site's data. |
| 2 | What does a delete remove? | **The library, its covers, the stay-unlocked key and the look-up choice.** The look-up choice goes back to "not chosen yet", so the next library is asked again. Theme and language stay: they belong to the device, not to the library, and keeping them means the screen does not switch language right after the delete. |
| 3 | How is it confirmed? | **One dialog from both places. I type DELETE (SLETT in Norwegian) before the red button arms.** Asking for the password on Profile would add friction and no security, since the login path skips it. One dialog is one code path and one set of strings. |
| 4 | Is it all or nothing? | **Yes.** The covers and the key go first, in one IndexedDB transaction. If that fails, nothing is removed and the message says so. Only after it succeeds does the library leave `localStorage`. |
| 5 | Can I keep a copy first? | **Yes, from both places, outside the dialog.** The encrypted export already works while the library is locked (`exportEncryptedBackup`), so the login panel offers it too. The dialog says that backup files I exported earlier are not touched. |

## 1. The wipe

### Pieces

| File | Status | Job |
|---|---|---|
| `Model/db.js` | changed | `clearLibraryStores()`: one `readwrite` transaction over the covers and session stores, `clear()` on both. Resolves on `oncomplete`, rejects on `onerror` and `onabort`, like `withStore`. |
| `Model/deleteLibrary.js` | new | `wipeLibrary(steps)`: runs the three steps in order and stops at the first failure. Pure, so Node can test it with fakes. |
| `Controller/Universal/deleteLibrary.js` | new | Opens the dialog, binds the real steps, then locks and reports. |
| `Model/persistence.js` | changed | `actuallyPersist()` only replaces a stored library, never creates one (below). |

### The order

```js
// steps = { clearStores, removeLibrary, resetLookups }
await clearStores();    // covers + stay-unlocked key, one transaction
removeLibrary();        // localStorage.removeItem(STORAGE_KEY)
resetLookups();         // setPref("lookups", "unset")
```

`wipeLibrary` returns `{ ok: true }`, or `{ ok: false, reason: "stores" }` when
`clearStores` throws. On that failure `removeLibrary` and `resetLookups` never
run, so the library is exactly as it was.

The order matters. The library envelope holds the salt that the cover key is
derived from, so covers left behind without it can never be opened again. That
is still clutter, and the first unlock of a new library would only prune it if
it ran. Clearing the stores first means a failure leaves nothing half done.

### After the wipe

On success the controller calls the existing `logout()`. It zeroes the keys,
clears the stay-unlocked key a second time (harmless), drops the decrypted
library and the cover cache from memory, and navigates to the start page. Then
it sets the notice "The library was deleted from this browser." in the info
tone. `logout()` navigates first, so the notice is set after it, the same way
`resetTransientViewState()` already expects.

The comment above `storeSessionKey()` in `Model/auth.js` says a delete-library
feature must call `clearSessionKey()`. `clearLibraryStores()` clears the whole
session store, which covers it. I update the comment to name the new function.

### A save cannot bring it back

`actuallyPersist()` encrypts first and writes afterwards. A save that started
just before the delete, in this tab or in another unlocked tab that has not yet
heard the storage event, would write the library straight back after
`removeLibrary()`. The start page would say "deleted" while the library sits
there again, without its covers.

So the write gets one more guard, next to the `libraryStale` check that runs
after encrypting: if `localStorage.getItem(STORAGE_KEY)` is `null`, it returns
without writing. A save only ever replaces a stored library. Register and
restore write their envelopes directly, not through this function, so creating a
library is untouched.

### On failure

On failure nothing navigates. The dialog has already closed, and the notice "The
library could not be deleted. Nothing was removed. Close other Spindle tabs and
try again." shows in the error tone where I pressed the button.

## 2. Profile

A new section goes last on the page, after Log out: destructive actions sit at
the end.

```
Delete library
Removes the library, its covers and the look-up choice from this browser.
Theme and language stay. This cannot be undone.      [ Delete library… ]
```

The heading uses `profile-settings-heading`, and the row has the same shape as
the Log out row. The button is `btn btn-danger`, the class the dialog's confirm
button already uses. The Backup section with Export sits
directly above, so keeping a copy is one scroll away.

## 3. The login page

Under the form and above the two footer links, a collapsed `<details>`:

```
▸ Can't open the library?
  There is no password recovery, and a damaged library cannot be repaired. If
  you have a backup, restore it below and log in with the password it was made
  with.
  [backupSection: Encrypted copy / Restore]
  Delete library
  Removes the library from this browser so you can start again.
  This cannot be undone.                                [ Delete library… ]
```

- The panel reuses `backupSection({ idPrefix: "login" })`. Its export and
  restore rows and its message line render the same as on the start page.
- Its open state lives in `model.viewState.loginForgotOpen`, toggled the same
  way as `welcomeBackupOpen`, so a re-render does not close it under me. It
  opens by itself while a backup message is showing, like the start page panel.
- The panel only renders when a library exists (`loadState().kind ===
  "encrypted"`). With no library there is nothing to forget a password to.
- A damaged library (`kind` is an error) shows the panel too, without the export
  row (`canExport: false`). A damaged library is the second case where deleting
  is the way out, and the reason the summary says "Can't open the library?"
  rather than only naming the password.
- Today the damaged-library banner says to "create a new library", but Register
  refuses while any envelope is stored, damaged or not. The banner's copy
  (`storage.corrupt`) now points at this panel instead, so it names a way out
  that works.

## 4. The dialog

`openDialog` gets one optional option, `confirmWord`. Without it the dialog is
unchanged.

With it:

- A labelled text input goes between the body and the actions. Its label reads
  "Type DELETE to confirm", with the word taken from the same string table as
  the word itself. It has `autocomplete="off"`, `autocapitalize="characters"`,
  `spellcheck="false"` and `enterkeyhint="done"`.
- The confirm button carries `aria-disabled="true"` until the input matches, and
  a press while it is disabled does nothing. I use `aria-disabled` rather than
  `disabled` so the button stays in the tab order and a screen reader can reach
  it and hear that it is unavailable.
- Enter in the input confirms only when the word matches.
- A press on the unarmed button, or Enter on a wrong word, is not silent. It
  shows "Type {word} exactly as shown." under the input in the error style,
  sets `aria-invalid="true"` on the input, adds the message to the input's
  `aria-describedby`, and moves focus to the input. The message clears as soon
  as the word matches.
- The unarmed button looks unavailable without relying on colour:
  `.btn[aria-disabled="true"]` gets reduced opacity and `cursor: not-allowed`,
  and under `forced-colors: active` its text and border use `GrayText`.
- Focus starts in the input, not on Cancel.
- Matching is `matchesConfirmWord(typed, word)`, exported from `dialog.js`:
  trimmed, upper-cased with `toUpperCase()`, compared exactly. "delete",
  " Delete " and "DELETE" all match; "DELET" and "DELETED" do not.

The title is "Delete the library?". The body:

> Your albums, covers and look-up choice are removed from this browser. Theme
> and language stay. Backup files you exported earlier are not touched and can
> still be restored. This cannot be undone.

The confirm button reads "Delete library" and uses `danger: true`.

## 5. Other tabs

`storageSync.js` already hears the library key change. A new branch comes before
the stale-copy one: when `event.key === STORAGE_KEY` and `event.newValue ===
null`, the library is gone.

- Unlocked tab: `logout()`, then the notice "This library was deleted in another
  tab." in the info tone. Marking the copy as stale would be wrong: there is
  nothing to reload into, and the decrypted library would stay in memory.
- Locked tab: `updateView()`, as today. The start page then shows "Create
  library" as the main action.
- A tab with the delete dialog open stays as it is. Its own confirm would find
  the stores and the key already empty, succeed, and land on the same page.

## 6. The info notice and focus

`authNotice()` renders every message as `auth-error` with `role="alert"`. A
successful delete is not an error. `setAuthMessage(key, tone = "error")` gains
a tone. `"info"` renders `class="auth-notice"` with `role="status"` and
`id="auth-notice"`, using the existing info colours of `backup-message-info`.
Every current caller keeps the error tone without changing a line.

A status region that is inserted with the page is often not read. The router
does not move focus on navigation, so after the delete focus would fall to
`<body>`, and the notice could go unheard. After a successful delete, the
controller focuses the start page's `<h1 id="welcome-heading">` (it gets
`tabindex="-1"`), and while an info notice is showing the heading carries
`aria-describedby="auth-notice"`. NVDA then reads "Spindle", then the notice,
once.

## 8. Verification

1. **`npm test`**:
   - `test/deleteLibrary.test.js`: the steps run in order; a throwing
     `clearStores` leaves `removeLibrary` and `resetLookups` uncalled and
     returns `reason: "stores"`; a clean run returns `ok: true`.
   - `matchesConfirmWord`: the matches and misses listed in § 4, plus SLETT
     and "slett".
   - The i18n key-parity test stays green with the new keys.
   - The replace-only guard: with `localStorage` stubbed as in
     `test/prefs.test.js`, a save with no stored envelope writes nothing, and a
     save over a stored one writes. If `persistence.js` will not import under
     Node, this check moves to the pane: start a save, delete, and confirm no
     envelope comes back.
2. **Browser pane**, on a throwaway library at `127.0.0.1` (never the library at
   `localhost`), at 375 px, 320 px and desktop width:
   - Profile: add an album with a cover, tick Stay unlocked, delete. Afterwards
     `localStorage` has no `spindle:v1:state`, both IndexedDB stores are empty,
     `lookups` is `"unset"`, and theme and language are unchanged. The start
     page shows the notice with `role="status"`, and "Create library" is the
     accent button.
   - The button stays inert until the word matches. A press on it, or Enter on
     a wrong word, shows the mismatch message and puts focus in the field.
     Escape and Cancel delete nothing.
   - After the delete, `document.activeElement` is `#welcome-heading` and its
     `aria-describedby` is `auth-notice`.
   - A hand-written damaged envelope: the banner names the login panel, the
     panel shows without the export row, and delete clears it so Create library
     works.
   - The login page panel: hidden with no library, shown with one, stays open
     across a re-render, export downloads, delete works without a password.
   - A forced `clearStores` failure (the IndexedDB transaction aborted from the
     console) leaves the library in place and shows the failure notice.
   - Two tabs, the first unlocked: deleting in the second locks the first, which
     shows "This library was deleted in another tab."
   - The Delete library row measures 44 px, and its button shares one bottom
     edge with the Log out button above it. In Norwegian at 320 px nothing in
     the row or the dialog clips or scrolls sideways.
   - Forced colours (emulated): the unarmed button reads as unavailable.
3. **NVDA, mine:** the dialog reads its title and body, the field reads its
   label, the disabled button says it is unavailable, and the notice on the
   start page is read once.
4. **My phone:** the panel on the login page, typing SLETT with the keyboard
   that opens, and the Norwegian strings.

## 9. Not in v0.9

- More than one library per browser. Spindle has one library per browser, so
  "delete a library" is "delete the library".
- Deleting the service worker's cache or uninstalling the app. The app shell
  holds no library data.
- An undo. The way back is a backup, and the dialog says so.
- Changing the password. It stays a separate decision.

## 10. Considered and rejected in the stress test

- **A reload between clearing the stores and removing the library.** The gap
  is one synchronous `removeItem` after the transaction commits. The worst case
  is a library that still opens, without its covers and without stay-unlocked.
- **Skipping the stores when IndexedDB will not open.** It would turn a
  passing failure into a half delete. A browser with IndexedDB switched off for
  good keeps today's way out: clearing the site's data.
- **A busy flag against a second press while the wipe runs.** Every step is
  idempotent: clearing empty stores and removing a missing key both succeed.
- **A password check on Profile.** Decision 3.
- **`Clear-Site-Data`.** It needs a server response, and it would also wipe
  theme and language, against decision 2.
- **One app-wide live region.** Focusing the heading with the notice as its
  description covers this flow without rebuilding `updateView`.
- **The service worker's cache.** It precaches same-origin app files only and
  skips every cross-origin request (`sw.js`), so it holds no library data.

## 11. Traps carried in

- `logout()` navigates, and navigation clears the auth notice. Set the notice
  after `logout()`, never before.
- A hidden pane defers a `<dialog>`'s `close` event. In pane scripts, wait for
  `close` or dispatch it by hand.
- Vite HMR splits the module graph. Restart the dev server before a pane script
  imports a model module.
- Use `127.0.0.1:<port>` for the throwaway library, so the test library at
  `localhost` is never what gets deleted.
- `git branch -r` is a stale cache. `gh api repos/malinfossum/spindle/branches`
  is the truth.
