# Spindle v0.4 — plan

Spec of record for v0.4. v0.3 is closed: the deployed app has the optional
format field, four library filters, no seeded material, log out in Profile, a
camera on the cover field, and real links for every page control.

v0.4 is one feature: **barcode scanning and metadata lookup**, decided yes on
2026-09-02 in `docs/v0.3-plan.md` § 7 and deferred here because it is the first
time the app talks to anything but the browser. This plan turns that ruling into
a shape I can build. The ruling itself is unchanged: off by default, one number
per press, one host, said plainly in the interface before the first request.

**Status:** built (commits from `727abba` on branch `v0.4`, 2026-09-16), pending merge. The Scan flow is not yet verified on a real device — see § 8.

**All decisions are made (2026-09-15).** Five questions were open; the answers
and what they traded away are in § 0.

---

## 0 — Decisions

| # | Question | Decision |
|---|---|---|
| 1 | What does a browser without `BarcodeDetector` (every browser on iOS) get? | **A typed barcode field, no polyfill.** Live scanning is layered on top only where the browser has the API. A WASM polyfill would be the app's first runtime dependency and would need `'wasm-unsafe-eval'` in `script-src` — a second CSP widening in the same release, in a direction the app has always refused. |
| 2 | One barcode came back as 25 releases (`720642442524`: several *Nevermind* pressings, one undated, two Nirvana bootlegs and a Megadeth bootleg on the same number). What then? | **Show a pick-list**, collapsed to distinct artist + title — those 25 become four. A single distinct hit fills without asking. MusicBrainz scores all 25 at 100, so "take the top hit" would be arbitrary. |
| 3 | What does a pick fill, and is the barcode kept? | **Artist, title, release year, format — only into fields still empty.** No cover art: the Cover Art Archive is a second host that redirects to a third. **The barcode is stored on the album** so a second scan of the same sleeve can say "already in your library" before any request. |
| 4 | How is consent given and remembered? | **A confirm dialog on the first press**, naming the host and what is sent; remembered as a plaintext pref; a standing note under the field; a **Profile toggle** to turn it off. Asking every time would be honest but exhausting on a shelf of 200 CDs, and the standing note keeps it visible. |
| 5 | Live scanner: camera stream or a barcode photo through a file input? | **Live stream in a `<dialog>`**, shown only where `BarcodeDetector` and `getUserMedia` exist. A photo needs no `Permissions-Policy` change but is one shot per attempt, and a blurry frame means starting over. |

## 1 — What leaves the device

Exactly this, and nothing until the user has said yes in the interface:

```
GET https://musicbrainz.org/ws/2/release/?query=barcode:<digits>&fmt=json&limit=100
```

No custom headers. `Referrer-Policy: no-referrer` is already set, so the request
carries no page URL. The response is CC0 data and is not stored anywhere except
the fields the user chooses to keep on the album.

`limit=100` is MusicBrainz's maximum. `720642442524` alone has exactly 25
releases, so a barcode reused more widely would lose releases past the first
page; the 25-release response is 34 KB, so asking for the maximum costs little.

Verified 2026-09-15 with `curl` against the live API:

- The response carries `Access-Control-Allow-Origin: *`, so a browser on
  `spindle-music.pages.dev` may read it. No key, no account.
- MusicBrainz asks for a `User-Agent` identifying the application. A browser
  cannot set that header and the documentation says nothing about clients that
  cannot; the request goes out with the browser's own. The IP rate limit is one
  request per second; the button being disabled while a lookup is in flight is
  what keeps to it — there is no queue and no retry.
- Two of three probes returned **`503 "The MusicBrainz web server is currently
  busy"`**. That is a normal state of the service, not an edge case, and it gets
  its own message.

Everyone who never presses the button keeps exactly the guarantee they have
today. That sentence is the whole design and the reason for every rule below.

## 2 — Data

- **`blankAlbum()` in `Model/model.js` gains `barcode: ""`.** One shape, one
  place, as the v0.3 rule says. `""` means not set.
- **`normalizeAlbums()` in `Model/persistence.js`** coerces `barcode` to a
  string of 8–14 ASCII digits, else `""`. This is the one read path and the
  import trust boundary, so a hand-edited backup cannot put anything but digits
  in the field — nothing downstream re-validates.
- **`Model/prefs.js`** gains `lookups: "off" | "on"`, default `"off"`, in
  `PREFS_DEFAULTS` and `PREFS_ALLOWED`. It lives in the plaintext prefs store on
  purpose: it must survive a reload before anyone has unlocked, and it is a
  display-level preference, not library data. Nothing else in the store changes.
- **`viewState.musicForm.lookup`** — transient, reset by
  `resetTransientViewState()` with the panels:

  ```js
  lookup: {
      status: "idle",   // "idle" | "busy"
      matches: [],      // [{ artist, title, year, format }], distinct
      owned: null,      // an album id when the barcode is already in the library
      filled: null,     // { artist, title } of the last fill, for the status line
      controller: null, // AbortController of the request in flight
  }
  ```

  `resetTransientViewState()` aborts `controller` before clearing the object,
  so a lookup never outlives the page that started it: navigating away while a
  request is in flight would otherwise let the response fill whatever
  `viewState.musicInfo` is current — the blank album on the next Add, or an
  unrelated album on Edit.

  Lookup errors go in `musicForm.errors.barcode`, the same holder as every other
  field error. The five keys are listed in § 7.

- **`Model/musicbrainz.js` (new)** is the only file that knows the host.
  `lookupBarcode(digits, signal)` builds the URL, fetches, and returns
  `matches`. No DOM, no model writes — a pure function of the number, so the
  VHS/DVD project can swap the source and keep everything else.

  This is the app's first external input, so the response is treated as
  untrusted: a body without an array `releases` is a failed lookup; a release
  without a string `title` or a non-empty `artist-credit` array is skipped;
  `year` is `parseInt(date.slice(0, 4))` and kept only as an integer between
  1000 and 2999, else `null`; `format` is mapped onto `ALBUM_FORMATS` and
  nothing else gets through. Artist and title are plain strings that every
  template escapes on render, the match list included.

  Collapse rule: one entry per distinct lower-cased `artist + title`, with the
  earliest non-empty `date` seen (year only) and the first mappable medium
  format seen. Order of first appearance. Mapping of MusicBrainz medium
  formats: a string starting with `CD` → `cd`; containing `Vinyl` → `lp`;
  `Cassette` → `cassette`; anything else → `other`; no media → `""`.

- **`findByBarcode(digits, exceptId)` in `Model/selectors.js`** returns the
  first album in `model.data.musicInfo` with that barcode and a different id,
  or `null`. Local, before any request. `exceptId` is the album being edited:
  without it every lookup from the edit page would find the record itself.

- **`model.app.canScan`**, set once at boot: `true` only when
  `navigator.mediaDevices?.getUserMedia` exists and
  `BarcodeDetector.getSupportedFormats()` resolves to a list containing
  `"ean_13"`. `"BarcodeDetector" in window` is not enough — desktop Chrome on
  Windows and Linux exposes the constructor and reports no formats, so the
  camera would open and no frame would ever match.

## 3 — The form row and the lookup flow

One new `form-row` in `View/Add_Or_Edit_New_Music/view.js`, placed after
Format and before Genre:

- **Barcode** input: `type="text"`, `inputmode="numeric"`, `pattern="[0-9 ]*"`,
  `autocomplete="off"`, `data-action-input="music-barcode"`, its own
  `field-error` span, `aria-describedby` pointing at the error span and — only
  while it is rendered — the standing note, so the attribute never names an id
  that is not on the page.
- **Look up** button, disabled and `aria-busy` while `lookup.status ===
  "busy"`. The Barcode input and this button sit in their own small
  `<form data-action-submit="barcode-lookup">`, the chip-input pattern: the
  page's main form is a `<div>`, so that is what makes Enter in the field work
  without a keydown handler. `pattern` on the input is not relied on — the
  controller validates, so a browser that skips native validation changes
  nothing.
- **Scan** button, `data-action="barcode-scan"`, rendered only when
  `model.app.canScan` is true. Everyone else sees only the typed field — no
  dead button.
- **Status line**, `role="status"`, in the row: `music.lookupWorking` while
  busy, `music.lookupFilled` with the artist and title after a fill, empty
  otherwise. `aria-busy` on a button announces nothing; this is what tells a
  screen-reader user that three fields just changed. Same device as the cover
  field's caption.
- **Standing note** under the row, always rendered when the pref is `on`:
  `music.lookupNote` ("Look-ups go to musicbrainz.org").
- **Owned note**, rendered when `lookup.owned` is set, `tabindex="-1"` so it
  can take focus: `music.barcodeOwned` with the artist and title, followed by
  a button on the existing `view-album` action with that album's `data-id`.
- **Match list**, `hidden` unless `matches.length > 1`: a `<ul>` with
  `aria-labelledby` on a `music.pickMatch` heading, holding buttons with
  `data-action="barcode-pick"` and `data-index`, each showing artist, title,
  year and format label — artist, title and year through `escapeHtml`, as
  every template does. Chip-panel pattern, so it needs no new CSS beyond the
  list itself.

The flow in `Controller/Edit_Music_Details/lookup.js` (new), registered in
`actions.js`:

1. `status === "busy"` → return; the button is disabled, but Enter in the
   small form is not. Read the field, strip spaces. Not 8–14 digits →
   `errors.barcode = "error.barcodeInvalid"`, render, focus the field, stop.
   Nothing sent.
2. `findByBarcode(digits, musicInfo.id)`. A hit that `lookup.owned` does not
   already hold sets it, renders the owned note, **moves focus to the note and
   stops**. The next press, with `owned` already set for this number, goes on
   — a second copy is legitimate. One press tells, the second press goes, and
   it is the same for someone who cannot see the note appear.
3. Pref `lookups` is `off` → `openDialog({ title: dialog.lookupTitle, body:
   dialog.lookupBody, confirmText: dialog.lookupConfirm, cancelText:
   dialog.lookupCancel })`. `false` → stop, field intact, nothing sent. `true`
   → `setPref("lookups", "on")` and continue.
4. `status = "busy"`, `controller = new AbortController()`, render, then
   `lookupBarcode(digits, AbortSignal.any([controller.signal,
   AbortSignal.timeout(10_000)]))`. When the promise settles, the result is
   applied only if `lookup.controller` is still the one this press created;
   otherwise the page has moved on and nothing is written.
5. Outcome:
   - **one match** → fill (rule below), `filled` set for the status line,
     `status = "idle"`, render, focus the first field that was filled, or the
     Barcode field if none was.
   - **several** → `matches` set, `status = "idle"`, render, focus the first
     button in the list. `barcode-pick` fills from `matches[index]`, empties
     the list, renders, focuses as above; a missing index (a stale render)
     returns without change.
   - **zero** → `errors.barcode = "error.barcodeNoMatch"`. The fields stay as
     typed so the person carries on by hand.
   - **HTTP 503 or 429** → `error.lookupBusy`. **Abort, network failure, or
     any other non-2xx** → `error.lookupFailed`. Unparsable JSON → the same.
   - Every error path sets `status = "idle"`, renders, and focuses the Barcode
     field. The form's top `role="alert"` banner is not used for these: they
     are about one field, and the existing rule keeps validation at fields.
6. Any `input` on the Barcode field clears `errors.barcode`, `matches`,
   `owned` and `filled` — the number the notes were about is gone.

**Fill rule.** `artist`, `title`, `releaseYear`, `format` — each written only
if the working copy's value is `""` or `null`. A lookup never overwrites
something the person typed. `barcode` is always set to the looked-up digits.
Nothing reaches `model.data` until Save, exactly as the cover preview.

**Edit page.** The row appears on both add and edit. On edit the field shows
the stored barcode; the flow is identical.

## 4 — The scanner

`View/Universal/scanner.js` (new), shaped like `dialog.js`: `openScanner()`
returns a promise of a digit string, or `null`.

- `getUserMedia({ video: { facingMode: "environment" } })`. A refusal,
  `NotFoundError`, or any other rejection → the dialog shows
  `error.cameraUnavailable` and a Close button; resolve `null` on close.
- On a stream: a `<video autoplay muted playsinline>` in the dialog, a
  `BarcodeDetector({ formats: ["ean_13", "upc_a", "ean_8"] })`, and a
  `requestAnimationFrame` loop that calls `detect(video)` at most five times a
  second (timestamp check, not `setInterval`, so it stops with the tab).
  `detect()` rejections are swallowed — a frame that cannot be decoded is
  just the next frame.
- First `rawValue` that is 8–14 digits → stop every track, close, resolve it.
- Cancel button, Esc, backdrop click, or `hashchange` → stop every track,
  close, resolve `null`. One exit function, as in `dialog.js`. A stream that
  outlives the dialog is the one thing that would make the browser's camera
  indicator lie, so track shutdown is the invariant, not the happy path.
- Focus returns to the Scan button, or to the Barcode field if the page was
  re-rendered underneath.

The controller writes the result into the Barcode field and
`viewState.musicInfo.barcode` and stops. **Look up is the user's next press**,
so the consent gate and the owned check sit in one place whatever way the
number arrived.

## 5 — Consent, Profile, About

- **Dialog copy** (EN; NO in § 7): title *"Look up this barcode?"*, body
  *"Spindle will send this barcode to musicbrainz.org to find the album —
  nothing from your library, and never on its own. As with any web request,
  MusicBrainz sees your IP address. You can turn look-ups off under
  Profile."*, buttons **Look up** / **Not now**. "Nothing else" would be a
  lie next to the network tab: the IP address and the browser's User-Agent go
  with every request, and this copy has to survive a sceptic reading it.
- **Profile**: one row in the Settings block on the `.profile-settings-row`
  shape, label `profile.lookups`, a `<select>` with `profile.lookupsOff` /
  `profile.lookupsOn`, `data-action-change="set-lookups"`. Changing it writes
  the pref and re-renders. Turning it off deletes nothing: barcodes already on
  albums stay, and the next Look up simply asks again.
- **About → Privacy** (`about.privacyBody`, both languages) is rewritten so
  "no third parties" is qualified in the same sentence: *"No server, no
  tracking, and no third parties — with one exception you choose: if you turn
  on barcode look-ups, the scanned number is sent to musicbrainz.org — nothing
  from your library — and, as with any web request, they see your IP address.
  …"* The rest of the paragraph (encryption, no recovery,
  export regularly) stays.

## 6 — Headers and the dev server

`public/_headers`:

- `connect-src 'none'` → `connect-src https://musicbrainz.org`. The policy
  still forbids every other host; this is the line that makes the promise
  enforced rather than stated.
- `camera=()` → `camera=(self)`. As it stands the policy refuses `getUserMedia`
  for our own origin before the user ever sees a permission prompt. The cover
  field survived it only because a file input does not use `getUserMedia`.
  Microphone and geolocation stay off.

`vite.config.js`: the dev replacement is a literal
`.replace("connect-src 'none'", …)`, which stops matching the moment the
header changes and would run the dev server with the HMR socket blocked and
no error. It changes to match the new value **and throws when the replace
found nothing**, so the next `_headers` edit fails at startup instead of
quietly.

## 8 — Verification

Before it is called done:

- **Coercion:** `normalizeAlbums` on `barcode` values `"720642442524"`,
  `"  7206 42442524 "`, `"abc"`, `12345`, `null`, missing → only the first
  survives as digits; the spaced one is `""` (spaces are stripped at the field,
  not at import).
- **Collapse:** the saved `720642442524` response (25 releases, kept out of
  the repo) → 4 matches, the first *Nirvana – Nevermind* with year `1991` and
  format `cd`. The same response with `releases` removed, and with one
  release's `title` set to a number, → `lookupFailed` and 3 matches
  respectively.
- **Abort:** navigate away with `fetch` stubbed to resolve after 2 s → the
  request is aborted and `viewState.musicInfo` on the next page is untouched.
- **Owned:** on the edit page, the album's own barcode does not trigger the
  owned note; on the add page it does, focus lands on the note, and `fetch` is
  not called until the second press.
- **Scan gate:** on the dev machine's Chrome, `getSupportedFormats()` is read
  and the Scan button renders only if `"ean_13"` is in the list.
- **Fill rule:** a form with `artist` typed and `title` empty, one match →
  artist untouched, title filled.
- **Consent gate:** pref `off`, `fetch` stubbed to throw → a Look up press
  opens the dialog and `fetch` is never called when it resolves `false`.
- **CSP:** one real lookup from the dev server succeeds; a `fetch` to any other
  host is refused by the policy in the console. `curl -I` on the deployed URL
  shows the new `connect-src` and `camera=(self)`.
- **Layout:** the Barcode row, match list and Profile row measured at 375 /
  768 / 1280 in both languages, 44×44 targets, zero horizontal overflow.
- **Scanner:** every exit path stops the tracks — asserted in the pane with a
  stubbed `getUserMedia` returning a stream whose tracks record `stop()`.
- **Owed to a real Android phone:** the Scan flow end-to-end with a sleeve. The
  pane cannot open a camera, so the report says "not verified on a device"
  until I have done it.

## 9 — Not in v0.4

Cover art from the Cover Art Archive (second and third host). A WASM polyfill
for iOS. Lookup by artist or title. Re-lookup from the detail page. A
`dateAdded` field. Each of these is a separate decision, not a loose end.

## 10 — Traps carried in from earlier plans

- A "Ready" item may already be built — nothing barcode-shaped exists in the
  code as of `f1b9ce5`; checked with grep on 2026-09-15.
- Every new album field goes in `blankAlbum()` and `normalizeAlbums()`, once.
- After any import sweep, grep every call site.
- `hashchange` is queued; a dialog opened in the same turn as a `navigate()`
  must drop the echo — `dialog.js` already does, and `scanner.js` copies it.
- The pane never fires `<dialog>` `close`; dispatch it by hand to exercise
  the exit function.
