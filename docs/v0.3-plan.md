# Spindle v0.3 — plan

Spec of record for v0.3. v0.2 is closed: the app is built, routed, deployed at
`spindle-music.pages.dev`, and served with real security headers.

v0.2 was about how Spindle is built and shipped. v0.3 is about using it. Almost
every item below came from Malin using the deployed app and finding it wanting,
which is the right source for a roadmap.

**Nothing here is started.** Items 1–3 need decisions from Malin before code;
they are marked **Needs a decision** with the question stated.

## 1 — The edit-album page

### The layout bug — fixed

**Done.** All three defects below are repaired: the four chip panels now render
with the `hidden` attribute instead of an inline `visibility` style, the flags
are called `panels.locationAdd` / `locationRemove` / `genreAdd` / `genreRemove`
and default to `false`, and they live in `model.viewState.musicForm` where
`resetTransientViewState()` closes them on every navigation. Measured on the
running app at 375px: each of the two rows was carrying two invisible 88px
boxes and is now 117px tall, growing to 205px only while a panel is open.

The original diagnosis, kept because the reasoning is the point:

The page is not broken; it is three small defects stacked, and together they
produce the tall empty bands under LOCATION and GENRE.

```
<form data-action-submit="new-location"
      style="visibility: ${model.app.showLocationInput ? "hidden" : "visible"};">
```

- **`visibility: hidden` hides the panel but keeps its box.** The add-a-location
  form, the remove-a-location form and their genre equivalents are all laid out
  at full height and then painted invisible. That is the empty space, exactly.
  `display: none` removes the box; `hidden` (the HTML attribute) does the same
  and is one fewer inline style, which the CSP would also thank us for.
- **The flags are named backwards.** `showLocationInput: true` means *do not*
  show it — all three default to `true` in `Model/model.js`, and `true` maps to
  `hidden`. Anyone reading `showGenreInput: true` will conclude the opposite of
  what it does. Rename to `genrePanelOpen`, defaulting to `false`.
- **They live in `model.app`.** These are transient view flags of one form, the
  same category as everything already in `model.viewState`. `model.app` is for
  app-wide state, and `viewState.js` already exists to reset transient state on
  navigation, which is what these should do and currently do not.

Fixing this is worth doing on its own, before any new field lands, because every
new field makes the page taller and the bug harder to see past.

### The fields — Needs a decision

"More options relevant to an album" is the right instinct, and the field list is
Malin's call because it decides what Spindle is *for*. Candidates, grouped:

- **Physical format** — CD / LP / cassette / other. Arguably the most valuable
  single field: it is in the app's own tagline, and it is the first thing you
  filter a physical collection by. Recommended if only one field is added.
- **Identity** — record label, catalogue number, barcode, pressing or edition,
  number of discs.
- **Condition and provenance** — sleeve and media condition (the standard
  Goldmine grades: M, NM, VG+, VG, G), where and when it was bought, price paid.
- **Personal** — rating, date added, times played.

Each one costs a form row, a string in two languages, a line in the detail view,
and a migration for libraries that already exist. That last part is not
optional: `Model/persistence.js` must carry old records forward, never drop
them, and the encrypted backups people already exported have to keep importing.

**Question for Malin: which of these four groups, and are any of them
required?** Everything currently required (artist, title, location, genre) is
required at save time, and the more required fields there are, the more the app
argues with someone typing in a stack of records at speed.

## 2 — Search

Five features were asked for. They are not equally cheap, and two of them raise
a privacy question the rest of the app has already answered.

- **Submit on Enter.** The search box is an `<input>` with `data-action-input`,
  so it filters as you type but never *commits*. Wrapping it in a form and
  giving it `data-action-submit` makes Enter navigate to the search page. Cheap,
  obviously right, no decision needed.
- **Clear the field after searching.** Same change, one line further on. Note
  it means the query lives only in the results heading, so that heading has to
  actually say what was searched for.
- **Suggestions while typing.** A datalist is the cheap version and behaves
  badly on mobile; a rendered listbox is the good version and needs arrow-key
  handling, `aria-activedescendant`, and an escape hatch. The data is free
  either way, since the library is in memory. Recommended: the rendered version,
  suggesting matching artists and titles, capped at eight.
- **Filter.** **Needs a decision:** filter by what? Genre and location are the
  two the model already has as first-class lists, and both are already how
  people think about a physical collection. Format, if item 1 adds it, becomes
  the obvious third. Year range is a slider nobody uses. Recommended: genre and
  location, as two dropdowns above the results, and add format later if it
  lands.
- **History.** **Needs a decision, and it is a privacy decision.** Spindle's
  promise is that the library never leaves the device and is encrypted at rest.
  Search history is a record of what someone looked for in their own collection,
  and it belongs on the same side of that line: stored inside the encrypted
  library, not in `localStorage` beside it, and cleared on logout. The cheap
  implementation — a plain `localStorage` key — would be the first unencrypted
  record of library contents in the app, which is a bad precedent for a nice
  convenience. Recommended: in-memory for the session, persisted into the
  encrypted library only if Malin wants it to survive a reload.

## 3 — Remove the hardcoded material

Three things were named. Two are clean removals; the third is a trap.

- **The demo albums.** Abbey Road, The Dark Side of the Moon and Ziggy Stardust
  are written out in full in **two** places: `Controller/Register/register.js`
  and `Model/model.js`. Duplicated seed data is its own bug waiting to happen,
  so this is a good removal. A new library then opens on the empty state, which
  already exists and is already translated.
- **The seeded genres and locations.** `SEED_EN` / `SEED_NO` give a new library
  Rock/Jazz/Country/Pop/EDM and Living room/Attic/Storage/Shop. **Removing them
  has a consequence worth naming:** genre and location are both *required* at
  save time (`editMusic.js`), so a brand-new empty library cannot save its first
  album until the user has created one of each through the ➕ panels — the same
  panels item 1 is about to fix. Recommended order: fix item 1 first, then
  remove the seeds, or the first run becomes a dead end.
- **The Norwegian navbar labels in `index.html` — recommended: keep them.**
  See below.

### Why the navbar text is not the same kind of hardcoding

`index.html` hand-writes the navbar, so `Hjem`, `Ønskeliste` and the rest are
literal text in the markup. On boot, `applyStaticText()` in
`View/Universal/chrome.js` overwrites every one of them with `t("nav.home")` and
friends. That is what "overwrites on boot" means: the HTML text is what the
browser paints for the first frame, and JavaScript replaces it the moment the
module graph runs.

So the labels are not a second source of truth that can drift — `chrome.js`
always wins, in both languages, and language switching already works. What they
are is a **first-paint placeholder**, and the question is only what should be in
that slot for the one frame before the script runs.

- Leave the Norwegian text: a Norwegian visitor sees nothing change, and an
  English visitor sees one frame of Norwegian. Norwegian is already the fallback
  language everywhere else in the app, so this is consistent.
- Empty the buttons: everyone sees one frame of blank buttons, the navbar
  reflows when text arrives, and for that frame the buttons have no accessible
  name at all — a screen reader landing there announces "button".

The second is worse, and the blank frame cannot be avoided by moving the labels
into the render path: `boot.js` is a module, modules are deferred by definition,
and there is always a paint before them. The only zero-flash option is the trick
`public/themePreload.js` uses — a classic synchronous script — which would mean
shipping the string tables outside the module graph to save one frame.

**Recommendation: leave the navbar alone.** If it still grates, the honest
smaller fix is `<html lang="no">`, which is hardcoded in the same file and is
also corrected on boot; that one at least has an accessibility argument, since
it is what a screen reader reads the page's language from.

## 4 — Log out moves into Profile

Ready to build, no decisions. It currently shares a slot with Log in in the
navbar (`syncNavbar()` swaps the label on the same button), which is why it gets
pressed by accident: the button that said "Log in" a moment ago now logs you
out, in the same position.

Moving it means the navbar button becomes login-only and hides when logged in,
and Profile gains a log-out control in the settings block. Worth pairing with a
confirm step, since logging out with unexported changes is the one irreversible
action in the app.

## 7 — Barcode scanning and metadata lookup — a product decision

The idea: point the phone at an album, have artist, title, year and cover come
back filled in. It would make cataloguing a shelf genuinely fast, which is the
difference between an app someone uses once and one they fill.

The obstacle is not difficulty. `BarcodeDetector` reads the EAN off the back of
a CD or LP in a few lines (Chrome and Android; Safari does not have it, so iOS
needs a WASM polyfill). **The obstacle is that a barcode is only a number.**
Turning it into "Miles Davis, Kind of Blue, 1959" means asking MusicBrainz or
Discogs, and that is a network request to a third party — from an app that ships
`connect-src 'none'` and tells people nothing leaves their device. Done once per
album, it is also a way of telling a stranger what records someone owns, one row
at a time.

OCR instead of a lookup does not rescue it: Tesseract.js is multi-megabyte WASM,
unreliable on stylised sleeve typography, and would still need a lookup to turn
a band name into a year and a genre.

So this is a decision about what Spindle is, not about what is buildable. If the
answer is yes, the least-bad shape is:

- An explicit button, off by default, that says plainly what it sends.
- It sends **only the scanned barcode**, never any part of the library.
- MusicBrainz rather than Discogs: no API key, no account, CC0 data.
- `connect-src` relaxed to exactly that one host in `public/_headers`, so the
  policy still forbids everything else.
- The About page's privacy section updated, because it currently promises "no
  third parties" without qualification.

That keeps the default promise intact for everyone who never presses the button.

## 8 — Carried over from v0.2

Found while building v0.2, deferred deliberately, still open:

- **`pushState` instead of `location.hash`.** Deletes `lastResolvedHash` and the
  whole echo-suppression mechanism. Deferred until the router had real browser
  mileage; it now has some. Note it would also make a `_redirects` file
  necessary on Cloudflare Pages, which fragment routing does not need.
- **Nav controls are `<button>`, not `<a href="#page">`.** Now that pages have
  URLs, the semantics convention argues for links.
- **Back during a confirm dialog.** `delete.js` awaits `openDialog()`, so a Back
  press re-renders `#app` under the open modal and the dialog's focus restore
  lands on a button that no longer exists. Belongs with the dialog.
- **`model.js:3` holds a live DOM node.** A Model file should not.
- **`clearFieldError` is DOM-patching** of the same shape the strength meter
  used to be.
