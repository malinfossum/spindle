# Spindle v0.3 — plan

Spec of record for v0.3. v0.2 is closed: the app is built, routed, deployed at
`spindle-music.pages.dev`, and served with real security headers.

v0.2 was about how Spindle is built and shipped. v0.3 is about using it. Almost
every item below came from Malin using the deployed app and finding it wanting,
which is the right source for a roadmap.

**All decisions are made (2026-09-02).** Items 1–3 and 7 were open questions;
Malin's answers are recorded in each section below, with the reasoning kept so a
later reader can see what was traded away. Item 7 is a yes, but it is scoped out
of v0.3 — see that section.

**Build order is not free choice.** Item 1 must ship before item 3 removes the
seeded genres and locations, or a new library cannot save its first album.

## 1 — The edit-album page

### The layout bug — fixed

**Done.** All three defects below are repaired: the four chip panels now render
with the `hidden` attribute instead of an inline `visibility` style, the flags
are called `panels.locationAdd` / `locationRemove` / `genreAdd` / `genreRemove`
and default to `false`, and they live in `model.viewState.musicForm` where
`resetTransientViewState()` closes them on every navigation. Measured on the
running app at 375px: each of the two rows was carrying two invisible 88px
boxes and is now 117px tall, growing to 205px only while a panel is open.

The original diagnosis, kept because the reasoning is the point:

The page is not broken; it is three small defects stacked, and together they
produce the tall empty bands under LOCATION and GENRE.

```
<form data-action-submit="new-location"
      style="visibility: ${model.app.showLocationInput ? "hidden" : "visible"};">
```

- **`visibility: hidden` hides the panel but keeps its box.** The add-a-location
  form, the remove-a-location form and their genre equivalents are all laid out
  at full height and then painted invisible. That is the empty space, exactly.
  `display: none` removes the box; `hidden` (the HTML attribute) does the same
  and is one fewer inline style, which the CSP would also thank us for.
- **The flags are named backwards.** `showLocationInput: true` means *do not*
  show it — all three default to `true` in `Model/model.js`, and `true` maps to
  `hidden`. Anyone reading `showGenreInput: true` will conclude the opposite of
  what it does. Rename to `genrePanelOpen`, defaulting to `false`.
- **They live in `model.app`.** These are transient view flags of one form, the
  same category as everything already in `model.viewState`. `model.app` is for
  app-wide state, and `viewState.js` already exists to reset transient state on
  navigation, which is what these should do and currently do not.

Fixing this is worth doing on its own, before any new field lands, because every
new field makes the page taller and the bug harder to see past.

### The fields — decided 2026-09-02

**Physical format only, and optional.** CD / LP / cassette / other. Nothing from
identity, condition, or personal goes in for now; each of those can be argued
for later against real use, which is a better argument than a guess made up
front.

Optional means the save-time required set stays exactly as it is — artist,
title, location, genre — so cataloguing a stack of records does not slow down.

What it costs, and all of it is required work, not optional polish:

- One `<select>` on the edit page, with an empty first option that means "not
  set" rather than a default of CD. A default would silently label every
  existing album a CD.
- `format: ""` added to the album record in **both** places it is written out —
  `Model/model.js` and `emptyList()` in `editMusic.js`. They are duplicated
  today, and the covers work has already been bitten once by editing one of a
  pair.
- Four strings per language (the label and three of the four values; "other"
  is a fourth), in `Model/i18n/en.js` and `no.js`.
- A line in the detail view, rendered only when the field is set.
- Migration in `Model/persistence.js`: an album loaded without `format` gets
  `""`, never `undefined`, and encrypted backups exported before this release
  must still import. The backup format carries whatever keys the record has, so
  the read path is where the default belongs.

Format then becomes the third search filter in item 2.

## 2 — Search

Three of the five features shipped with the navigation restructure on
2026-08-31: the search box is a real `<form>` so **Enter commits**, the field
**clears** into a results heading that says what was searched for, and
**suggestions** render through the ARIA combobox pattern in
`View/Universal/searchSuggest.js`. Two remain.

### Filter — decided 2026-09-02

**Four filters: genre, location, format, and decade.** Genre and location are
already first-class lists on the model. Format arrives with item 1. Decade is
"age" — and it is free, because `releaseYear` **already exists** on the album
record (`Model/model.js`, `editMusic.js`) and has since v0.1. A decade
dropdown built from the years actually present in the library needs no new
field and no migration.

One narrowing, deliberate. The ask was "and any relevant information", and a
filter per field is the wrong shape: every filter is a control, two
translations, and another dimension of combined state to render an empty result
for. Four is already the point where the controls need to collapse behind a
"Filter" disclosure on mobile. If a fifth earns its place through use, it can
be added; the set is not meant to grow to match the form.

**Note on "age".** This is *release* year, not *date added* — Spindle has never
stored when an album was added, and album ids are random (`Math.random()`), so
they cannot stand in for it. Sorting by recency works only because it reads
position in `model.data.musicInfo`. A real `dateAdded` was offered before and
deferred; it is still deferred, and it is the only way "oldest in my collection"
could ever mean "longest owned".

### History — decided 2026-09-02

**In-memory for the session.** It lives in `model.viewState`, dies on reload,
and is cleared on logout with the rest of the decrypted state. Nothing is
written to `localStorage`, so the app still holds no unencrypted record of
library contents anywhere — which is the property that made the cheap version
unacceptable. If it later needs to survive a reload, it goes inside the
encrypted library, never beside it.

## 3 — Remove the hardcoded material — decided 2026-09-02

**Remove the first two, leave the navbar.**

- **The demo albums — remove.** Abbey Road, The Dark Side of the Moon and Ziggy
  Stardust are written out in full in **two** places,
  `Controller/Register/register.js` and `Model/model.js`. A new library then
  opens on the empty state, which already exists and is already translated.
- **The seeded genres and locations — remove, but not first.** `SEED_EN` /
  `SEED_NO` give a new library Rock/Jazz/Country/Pop/EDM and Living
  room/Attic/Storage/Shop. Genre and location are both *required* at save time
  (`editMusic.js`), so a brand-new empty library cannot save its first album
  until the user has created one of each through the ➕ panels — the panels item
  1 repairs. **Order is load-bearing: item 1 ships first, then the seeds come
  out**, or the first run becomes a dead end.
- **The Norwegian navbar labels in `index.html` — leave them.** Reasoning
  below; it is a first-paint placeholder, not a second source of truth.

### Why the navbar text is not the same kind of hardcoding

`index.html` hand-writes the navbar, so `Hjem`, `Ønskeliste` and the rest are
literal text in the markup. On boot, `applyStaticText()` in
`View/Universal/chrome.js` overwrites every one of them with `t("nav.home")` and
friends. That is what "overwrites on boot" means: the HTML text is what the
browser paints for the first frame, and JavaScript replaces it the moment the
module graph runs.

So the labels are not a second source of truth that can drift — `chrome.js`
always wins, in both languages, and language switching already works. What they
are is a **first-paint placeholder**, and the question is only what should be in
that slot for the one frame before the script runs.

- Leave the Norwegian text: a Norwegian visitor sees nothing change, and an
  English visitor sees one frame of Norwegian. Norwegian is already the fallback
  language everywhere else in the app, so this is consistent.
- Empty the buttons: everyone sees one frame of blank buttons, the navbar
  reflows when text arrives, and for that frame the buttons have no accessible
  name at all — a screen reader landing there announces "button".

The second is worse, and the blank frame cannot be avoided by moving the labels
into the render path: `boot.js` is a module, modules are deferred by definition,
and there is always a paint before them. The only zero-flash option is the trick
`public/themePreload.js` uses — a classic synchronous script — which would mean
shipping the string tables outside the module graph to save one frame.

**Decided: leave the navbar alone.** If it still grates, the honest
smaller fix is `<html lang="no">`, which is hardcoded in the same file and is
also corrected on boot; that one at least has an accessibility argument, since
it is what a screen reader reads the page's language from.

## 4 — Log out moves into Profile

Ready to build, no decisions. It currently shares a slot with Log in in the
navbar (`syncNavbar()` swaps the label on the same button), which is why it gets
pressed by accident: the button that said "Log in" a moment ago now logs you
out, in the same position.

Moving it means the navbar button becomes login-only and hides when logged in,
and Profile gains a log-out control in the settings block. Worth pairing with a
confirm step, since logging out with unexported changes is the one irreversible
action in the app.

## 5 — Profile page tidy-up

Two things, both ready.

- **The album grid comes off the profile page.** Profile is the settings screen;
  the albums are already on Home. `getProfileAlbums()` and the grid markup go
  with it.
- **The backup rows need aligning.** "Choose File" and "Export" sit at different

  columns — label and description on the left, control right-aligned — not a

## 7 — Barcode scanning and metadata lookup — decided 2026-09-02

**Yes, build it — opt-in, and the app must say plainly what using it means.**
Malin's reason is the right one: this is what turns Spindle from something
catalogued once into something actually used, because typing a shelf in by hand
is the reason most collections never get entered.

The constraint is unchanged. `BarcodeDetector` reads the EAN off the back of a
CD or LP in a few lines (Chrome and Android; Safari lacks it, so iOS needs a
WASM polyfill). **A barcode is only a number** — turning it into "Miles Davis,
Kind of Blue, 1959" means asking a third party, from an app that ships
`connect-src 'none'` and promises nothing leaves the device.

So the shape is fixed by the promise, not by convenience:

- **Off by default.** A button the user presses, never a background lookup.
- **Sends only the scanned barcode.** No part of the library, no identifiers,
  no history. One number per press.
- **MusicBrainz, not Discogs**: no API key, no account, CC0 data.
- **`connect-src` relaxed to exactly that one host** in `public/_headers`, so
  the policy still forbids everything else. This is the line that makes the
  guarantee enforced rather than promised.
- **The user is told, in the interface, before the first request** — not only in
  the About page. Malin's condition: it must be visible what choosing this
  means. So a first-use explanation naming the host and what is sent, and a
  standing indicator wherever the feature sits, in plain language rather than a
  privacy-policy paragraph.
- **The About page's privacy section is rewritten**, because it currently
  promises "no third parties" without qualification. That sentence becomes
  false the moment this ships, and it must not be allowed to.

Everyone who never presses the button keeps exactly the guarantee they have
today. That is the whole design.

**Not in v0.3.** This is the largest item on the list — a device API with an iOS
fallback, a network path, a CSP change, and new privacy copy in two languages —
and three of its four parts are things the app has never done before. It lands
after items 1–6 and 8, as the headline of v0.4, with its own spec.

## 8 — Carried over from v0.2

Found while building v0.2, deferred deliberately, still open:

- **`pushState` instead of `location.hash`.** Deletes `lastResolvedHash` and the
  whole echo-suppression mechanism. Deferred until the router had real browser
  mileage; it now has some. Note it would also make a `_redirects` file
  necessary on Cloudflare Pages, which fragment routing does not need.
- **Nav controls are `<button>`, not `<a href="#page">`.** Now that pages have
  URLs, the semantics convention argues for links.
- **Back during a confirm dialog.** `delete.js` awaits `openDialog()`, so a Back
  press re-renders `#app` under the open modal and the dialog's focus restore
  lands on a button that no longer exists. Belongs with the dialog.
- **`model.js:3` holds a live DOM node.** A Model file should not.
- **`clearFieldError` is DOM-patching** of the same shape the strength meter
  used to be.
