# Spindle v0.7 — plan

Spec of record for v0.7. v0.6 is closed: Spindle has its mark, installs from
the Profile row and opens with no network. The phone pass ran 2026-09-28 and
passed: the app opens in airplane mode, a look-up there says the connection is
the problem, and the same look-up online fills the form at once.

v0.7 takes two chores off the Add album form. A phone photo of a sleeve comes
with the table around it, so every cover I photograph gets a square frame on
the sleeve that I can adjust before it is saved. And a look-up now ticks the
genres as well, adding the ones my list does not have yet — I still read the
form before I save it.

**Status:** designed and stress-tested 2026-09-28 (security, privacy,
accessibility, loopholes); its fourteen fixes are folded into §§ 1–4 and what
I chose not to fix is in § 7. Task plan to follow.

**All decisions are made (2026-09-25 and 2026-09-28).** They are in § 0.

## 0 — Decisions

| # | Question | Decision |
|---|---|---|
| 1 | Does cropping belong in v0.6? | **No — it is v0.7's headline** (2026-09-25). Every photo I take or upload gets a best-guess square frame I can drag or pinch before it is saved. Plain canvas, no new dependency and no WebAssembly, so the v0.4 CSP ruling stands. Look-up covers arrive cropped and skip it. |
| 2 | When does the crop editor appear? | **Every time**, as a dialog straight after the photo is picked, opened on the guess. One tap on Use when the guess is right. v0.5 § 8 found an automatic crop unreliable enough to need an adjust step anyway, and this way I always see exactly what gets saved. The alternative — apply the guess silently, adjust on request — hides a bad crop in a small preview. |
| 3 | How is the frame guessed? | **By background colour.** The ring along the photo's edge is the table, the floor or the bed; everything that clearly differs from it is the sleeve. A guess that is not roughly square, or too small, falls back to the centre. Edge detection was the other candidate and loses: cover art is full of strong edges of its own. |
| 4 | How is the frame adjusted? | **A fixed square with the photo moving under it** — the profile-picture pattern. Drag moves, pinch and the wheel zoom, and the photo can never leave a gap in the square. A resizable frame with corner handles was rejected: small targets on a phone, awkward from a keyboard, more code for the same result. |
| 5 | What is kept? | **The cropped result only.** No original is stored; changing a crop later means picking the photo again. No straightening of a sleeve shot at an angle. |
| 6 | Can a look-up fill the genre? | **Yes — tick every genre MusicBrainz gives that passes the vote cut-off, on my list or not.** One more request to musicbrainz.org, a host `connect-src` already allows. Ticks are only ever added, never taken away. |
| 7 | Which genres count? | **At least a quarter of the top genre's votes, at most three.** Nevermind's release group votes grunge 48, alternative rock 20, rock 5, punk rock 3 — that gives Grunge and Alternative rock, not every genre someone once voted for. |
| 8 | When does a new genre join my list? | **When I save the album.** Until then it is ticked in the form with a **New** label and stored nowhere. Untick it, or cancel, and it never reaches the list — the same rule a cover already follows. |
| 9 | What about my Norwegian genre names? | **Not needed.** My genres are broad English names, so matching is English and case-insensitive. A new genre is added with a capital first letter: "alternative rock" becomes "Alternative rock". |

## 1 — Cover cropping

### Pieces

| File | Status | Job |
|---|---|---|
| `View/Universal/cropGuess.js` | new | The best-guess square. Pixels in, `{ x, y, side }` out. Draws nothing, so the Node suite tests it on made-up pixel arrays. |
| `View/Universal/cropFrame.js` | new | The frame's maths: clamping, zoom around a point, drag, keyboard steps. Pure functions over `{ x, y, side }` and the photo's size. |
| `View/Universal/cropDialog.js` | new | The dialog: builds it, draws the frame, resolves with the chosen square or `null`. Built on `showModal()` like `View/Universal/dialog.js` and `scanner.js`, text written with `textContent`. |
| `Controller/Edit_Music_Details/crop.js` | new | Pointer, wheel and key handling for the dialog, turned into `cropFrame.js` calls. |
| `View/Universal/downscale.js` | changed | Split into `decodeCover(blob)` → `ImageBitmap` or `null`, and `encodeCover(bitmap, square)` → data URL or `null`. `downscaleCover(blob)` stays as decode + encode with no square, for the look-up path. |
| `Controller/Edit_Music_Details/editMusic.js` | changed | The cover handler: sniff → decode → guess → dialog → encode → preview. |

Image helpers already live in `View/Universal/` beside `sniff.js` and
`downscale.js`; the two pure ones go there for the same reason.

### The flow

1. A file arrives at `#music-cover`. `sniffImageType` checks its bytes as
   today; a file that fails stops here with `error.imageInvalid`.
2. The form goes busy (`music.coverWorking`) and `decodeCover` decodes it once
   with `imageOrientation: "from-image"`, so every coordinate below is in the
   photo's upright pixels.
3. `guessSquare` runs on a copy at most 256 px on the long side and returns a
   square in the full photo's pixels.
4. The crop dialog opens on that square.
5. **Use** → `encodeCover(bitmap, square)` → `form.coverPreview`, as today.
   **Cancel** → nothing changes: an earlier cover stays, and the file input is
   cleared so picking the same photo again still fires `change`.
6. The bitmap is closed on every exit, and focus returns to the cover picker.

**A photo that cannot be decoded or encoded is refused, not stored raw.** Until
now a failed downscale kept the file as it came — EXIF and GPS included, and
after v0.7 uncropped as well, the opposite of what I just chose in the dialog.
So a failed `decodeCover` (no dialog opens) or a failed `encodeCover` (after
Use) sets `error.coverProcess` on the cover field, clears the input and keeps
any earlier cover. The raw fallback and `readFileAsBase64` go. It is rare —
the bytes were already checked in step 1 — and when it happens the message
says so instead of storing something I did not ask for.

### The guess

- **Background.** The ring along the edges — the outer 4 % of each side — gives
  the background colour, taken as the median of each channel.
- **Busy background.** If more than 30 % of the ring is far from that colour,
  the background is not plain (a full shelf) and the frame starts in the centre.
- **Sleeve.** A pixel is foreground when its distance from the background —
  over R, G, B **and alpha**, so a PNG on a transparent ground works too — is
  over a threshold. The box runs from the first to the last row and column
  where more than a fifth of the pixels are foreground.
- **Sanity check.** The box must be roughly square (width ÷ height between
  0.8 and 1.25) and cover at least a quarter of the photo. Otherwise: centre.
- **Square.** The box's longer side, centred on the box, clamped inside the
  photo.
- **Centre fallback.** The largest square that fits, centred.

Every number above is a named constant at the top of `cropGuess.js`. They are
first guesses; they get tuned on real phone photos of my sleeves (§ 4), which
stay out of the repo.

### The dialog

- **Layout, phone first.** Full screen on a phone, centred and at most about
  480 px wide on a desktop. On top, the square — as wide as the screen allows,
  showing the photo only inside it. Under it one hint line (`crop.hint`), then
  one row: **−**, **+**, **Cancel**, **Use**. All four are 44 px tall and share
  one bottom edge; Use is the primary button. When the row does not fit — 320 px
  wide or 200 % text — it wraps as two pairs (zoom, then Cancel and Use), never
  a horizontal scroll.
- **Once only.** The dialog resolves once: after Use or Cancel every button is
  disabled, so a double tap cannot encode twice.
- **Canvas, not `<img>`.** The photo is drawn on a `<canvas>` sized to the
  square in CSS pixels × `devicePixelRatio`, redrawn on `requestAnimationFrame`.
  An `<img>` would need a `blob:` URL, and `img-src` allows `'self' data:`
  only — a canvas needs no change to the CSP.
- **Limits.** Zoomed out, the square is the photo's shorter side. Zoomed in, it
  stops at a quarter of that — past four times, a phone photo no longer has the
  detail for a 700 px cover — but never below 200 px of the photo (or the whole
  shorter side, if the photo is smaller), so a small image cannot be zoomed
  into a 12 px cover. The photo can never be moved far enough to leave a
  gap in the square. **−** and **+** are disabled at their limits.
- **Pointer.** Pointer Events with `setPointerCapture` and `touch-action: none`
  on the square. One pointer drags; two pinch, zooming around their midpoint.
  The wheel zooms around the cursor, 10 % a notch.
- **Keyboard.** Focus starts on the square: a `<div role="application"
  tabindex="0">` labelled `crop.stage`, with the hint as its description and the
  canvas inside it `aria-hidden`. The role is what makes a screen reader pass
  arrow keys through instead of reading the page with them — this is the one
  widget in the app where that is right. Its focus ring is an `outline`, so it
  survives `forced-colors`. Arrow keys move 2 % of the
  square, Shift + arrow 10 %; `+` and `-` zoom 10 %; Enter is Use; Escape is
  Cancel (the native `<dialog>` behaviour).
- **No pinch needed.** The − and + buttons zoom with a single tap, which is
  the single-pointer alternative WCAG 2.5.7 asks for alongside drag.
- **Leaving the page.** Back, forward or a link while the dialog is open closes
  it with `null`, as the confirm dialog and the scanner already do. Nothing is
  kept.

### Output

The chosen square is cut from the full-resolution bitmap and drawn to a
square canvas of `min(700, side)` px — never enlarged — then encoded as WebP at
0.82, with the PNG fallback `downscale.js` already accepts. The re-encode
drops EXIF, GPS included, exactly as today. Covers from a look-up still go
through `downscaleCover` with no square.

On the Edit page a newly picked photo goes through the same dialog. Covers
already saved are not touched.

## 2 — Genre from the look-up

### Pieces

All in `Model/musicbrainz.js`, beside the barcode look-up and the cover:

- `GENRES_URL(releaseGroupId)` →
  `https://musicbrainz.org/ws/2/release-group/<id>?inc=genres&fmt=json`.
  Verified 2026-09-28: `Access-Control-Allow-Origin: *`, and Nevermind's
  release group answers with four voted genres. It throws on an id that fails
  `isReleaseGroupId`, so nothing but a UUID ever reaches the path.
- `fetchGenres(releaseGroupId, signal)` → `{ status: "ok", genres }` or
  `{ status: "failed" }`. A rejection is fetch's own and is left to the caller,
  like `lookupBarcode`.
- `pickGenres(genres)` — pure, and the trust boundary. Anything that is not an
  array gives no genres; an entry whose `name` is not a string or whose `count`
  is not a finite number is dropped. Each name is cleaned (trim, strip control
  characters, collapse whitespace, cap at 40 characters, drop empties). Sorted
  by votes, ties by name so the result never depends on response order; keeps
  those with at least a quarter of the top count, at most three.
- `genreKey(name)` — pure. Lower case, hyphens and runs of whitespace as one
  space. Every comparison below goes through it, so MusicBrainz's "hip hop"
  finds my "Hip-hop" instead of adding a twin.
- `mergeGenres(list, picked)` — pure. Returns the indexes on my list to tick
  (matched by `genreKey`) and the names that are new, each with a capital
  first letter.
- `commitGenres(list, pending)` — pure. Appends the ticked new names to the
  list, skipping any whose key is now on it (I may have added the same one by
  hand in the meantime), and returns the new list with each name's index.

### The flow

1. A match is filled — at once when there is one, on a pick when there are
   several. `fill()` in `lookup.js` fires the genre request beside the cover
   request, on the **same `AbortController`**, so editing the number, starting
   another look-up or leaving the page stops both. A late answer from an
   aborted look-up can never tick anything.
2. **Rate limit.** MusicBrainz allows about one request a second. The look-up
   records when the barcode search answered; the genre request waits until
   1.1 s have passed since then. After a pick that has usually passed already.
3. The release group comes from the match (`match.releaseGroupId`). An empty
   one skips the genre request entirely.
4. The answer runs through `pickGenres`, then `mergeGenres` against
   `model.data.genre`. Known genres are added to `musicInfo.genre`; new ones go
   to `musicForm.pendingGenres`, ticked. Nothing already ticked is unticked.
5. The status line that says `music.lookupFilled` gains a second sentence,
   `lookup.genres` — "Genre: Grunge, Alternative rock." Ticked boxes alone say
   nothing to a screen reader.

A busy server, a failed request, an abort or no genres at all: nothing is
ticked and nothing is said. The rest of the look-up has already worked.

### In the form

- `pendingGenres` is part of the blank form state and is reset with it, like
  `lookup`.
- Pending genres render after my list's checkboxes, ticked, each with a small
  **New** label (`music.genreNew`) inside the checkbox's `<label>`, so a screen
  reader hears "Grunge, New" and not just "Grunge". Unticking one keeps it in
  the form, unticked, so a mis-tap can be undone.
- **Validation.** Genre is required. A ticked pending genre satisfies it, the
  same as a ticked one from my list.
- **Save.** The save path runs `commitGenres`, persists the grown list and adds
  the new indexes to the album. Unticked pending genres are dropped. Cancel
  drops them all.

Names from MusicBrainz are untrusted input: cleaned by `pickGenres`, and
escaped wherever they render, like every other field.

## 4 — Verification

1. `npm test` — `guessSquare` on made-up images (a sleeve on a plain ground
   gives its box, on a transparent ground too; low contrast, a busy ring and a
   long thin shape give the centre); `cropFrame` limits including the 200 px
   floor on a small image, zoom around a point, drag and key steps;
   `pickGenres` on Nevermind's real counts → Grunge, Alternative rock, and on a
   malformed response (not an array, a numeric name, a `NaN` count, a
   500-character name) → only the valid, capped entries; tied counts in either
   order → the same result; `mergeGenres` and `commitGenres` — case, "hip hop"
   against "Hip-hop", capital letter, no duplicates, an unticked pending genre
   never committed.
2. **Tuning.** Three to five phone photos of my sleeves, on a table and on a
   shelf. They stay in a local folder outside the repo, never become test
   fixtures (the fixtures are made-up pixels), and are deleted once the
   constants are set. Every photo gets a sensible first frame or the centre.
3. Browser pane, at 375 px, 320 px and desktop width: the dialog opens on the
   guess; the control row measures 44 px with one shared bottom edge, and
   wraps as two pairs at 320 px; keyboard only — move, zoom, Enter, Escape;
   Cancel keeps the old cover; focus returns to the picker; the saved cover is
   square and at most 700 px. A corrupt file with a valid header shows
   `error.coverProcess` and keeps the old cover.
4. Browser pane: a real look-up ticks the genres, shows the new ones with
   their label, and the status line names them. Save adds the new ones to the
   list; cancel adds nothing.
5. **The gate before merging:** the PR's Cloudflare preview URL — the genre
   request succeeds under the deployed CSP (`npm run preview` sends no
   headers).
6. My phone: pinch and drag on real sleeves, and one full add from the camera.

## 5 — Not in v0.7

- Straightening a sleeve photographed at an angle.
- Re-cropping saved covers, or keeping original photos.
- Cropping look-up covers — they arrive square.
- Translating genres. They stay English.
- Frame shapes other than square. VHS and DVD sleeves are not square; that
  belongs to the next project, which can take the ratio as a parameter.
- iOS verification — a friend tests on an iPhone once Spindle is finalized.

- **Implementer subagents run on Sonnet or better.** A cheaper model rewrote
  `Model/i18n/en.js` from 317 lines to 44 in v0.5 and reported success; the
  Node suite does not cover the string tables.
- **The browser pane cannot pinch.** Two-pointer gestures are proven by the
  `cropFrame.js` tests and on my phone, not in the pane.
- **A hidden pane lays out at 0 px wide** — resize before measuring anything.
- **Vite HMR splits the module graph** — restart the dev server before driving
  the model from `javascript_tool`.
- **`npm run preview` has no headers** — the Cloudflare preview URL is where
  the CSP is real.

## 7 — Considered and rejected in the stress test

- **A size cap on the genre response.** A release group's JSON is a few
  kilobytes and `pickGenres` keeps three names at most; the cover's 2 MB cap
  exists because a cover is stored, and a genre response is not.
- **A decompression bomb in a picked photo.** A huge-dimension image could
  exhaust memory in `createImageBitmap`, but it is a file I picked on my own
  device, and the worst case is my own tab crashing. The same was true of
  every version before this one.
- **Rewording the privacy text for the genre request.** It says the scanned
  number goes to musicbrainz.org and nothing from my library does. The genre
  request asks about the same album by its MusicBrainz id — still nothing
  from the library — and only runs after I consented to look-ups.
- **Announcing the zoom level.** A spoken percentage after every step is noise;
  the − and + buttons going disabled at the limits is the state that matters.
- **Better capitals for new genres.** "r&b" becomes "R&b". Rare, and unticking
  it and adding my own name takes seconds.
- **Two tabs adding the same genre.** Adding one by hand has the same gap
  today; `storageSync.js` already governs two tabs on one library.
